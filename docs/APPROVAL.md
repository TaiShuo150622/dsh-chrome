# 审批（approval）说明

> 关联：[设计文档](DESIGN.md) §4.6 · [分阶段计划](ROADMAP.md) §6
> 一句话：**审批 = 模型想对浏览器做「会改变外部世界或可能外发数据」的动作时，先停下来在 DSH 界面里问人；人点允许才执行，拒绝就返回失败，模型不得绕过。**

## 1. 为什么浏览器动作需要审批

DSH 本身的权限预设（read-only / workspace-write / danger-full-access）管的是**本机文件与命令**；浏览器是另一类风险面：

- **对外副作用**：提交表单、下单、发消息、发帖、改设置、删数据——做了就收不回。
- **数据外发**：上传文件、读剪贴板、把页面内容发给第三方站点。
- **账号与身份**：操作的是用户已登录的账号，误操作影响的是真实身份。
- **页面不可信**：页面里的文字可能是诱导（prompt injection），不能把页面内容当指令。

所以浏览器动作需要**独立的、动作级的确认**，不能只依赖会话级的权限预设。Claude in Chrome 与 Codex 都是这么做的（站点级授权 + confirmations）。

## 2. 用户会看到什么

工具调用在 DSH 里暂停，弹出一张卡：

```
DSH Chrome 请求操作浏览器
动作：点击「提交订单」按钮
站点：shop.example.com（本会话首次操作该站点）
影响：可能提交订单并产生扣款
[ 允许一次 ]  [ 本会话信任此站点 ]  [ 拒绝 ]
```

- 点「允许一次」：执行这一次；下次同类动作再问。
- 点「本会话信任此站点」：本会话内该站点的普通动作不再问（**硬敏感动作仍然每次问**）。
- 点「拒绝」：动作不执行，模型收到 `APPROVAL_DENIED`，并被要求向你解释/换方案。
- 超时（默认 120s）或你关掉会话：动作不执行，返回 `TIMEOUT`。

## 3. 什么会问、什么不会

| 类别 | 例子 | 默认行为 |
|---|---|---|
| 读取 | `chrome_snapshot` / `chrome_screenshot` / `chrome_tabs list` | **平衡模式**：自动执行（数据只进当前会话）；**严格模式**：新站点首次读取询问一次 |
| 普通写入 | 点击/输入/滚动/导航/后退/前进/刷新/新标签 | 首次到该站点询问一次；本会话信任后放行 |
| 硬敏感（始终问，不因信任放行） | 上传文件、下载落盘、执行 JS（V2）、读/写剪贴板（V3）、向密码/支付字段输入、检测到的表单提交 | 每次都问 |
| 受保护页面 | `chrome://`、扩展商店 | 直接拒绝（`PROTECTED_PAGE`），不弹审批 |
| 登录 / CAPTCHA | 页面要求登录或人机验证 | 不是审批：截图 + 提示交还用户处理；模型等待你完成后继续 |

> 注：上表是**建议默认值**；P1 用「平衡模式」，可配置切换（见 §5）。

## 4. 与 DSH 自身权限/审批的关系

| 层 | 管什么 | 我们如何使用 |
|---|---|---|
| DSH 会话权限预设（read-only / workspace-write / danger-full-access） | 本机文件、命令、审批策略 `ask/never` | 遵守它对文件/命令的约束；**浏览器动作不因 `never` 被静默放行** |
| DSH Host 审批服务 `ctx.approval` | 统一审批入口，按会话策略决定是否弹卡 | P1 优先用它；若在 `danger-full-access` 下会被自动放行，则改用 `ctx.userQuestions.ask` 的确认卡 |
| 插件级浏览器审批（本插件） | 浏览器动作的动作级确认 | 默认开启；提供严格度配置；硬敏感动作不受配置影响 |
| Plugin Manager 安装/启停插件 | 插件本身的安装审批 | 属于 DSH 系统审批，与本说明无关 |

**关键决定**：浏览器审批默认**独立于** DSH 会话预设。原因：`danger-full-access` 是为了让本机开发顺畅，不代表允许模型静默提交订单或上传文件。若你希望「跟随会话预设」，可在配置里改（见 §5 的 `follow-dsh` 模式）。

## 5. 严格度模式（配置项 `approval.mode`）

**已拍板（2026-10-17）：默认 `follow-dsh`。** 含义：普通动作跟随 DSH 会话的审批策略；硬敏感动作不受策略影响、始终问。

| 模式 | 读取 | 普通写入 | 硬敏感 | 适用 |
|---|---|---|---|---|
| `strict` | 新站点首次询问 | 每次询问（可信任站点） | 始终问 | 首次使用、敏感账号 |
| `balanced` | 自动 | 新站点首次询问，可本会话信任 | 始终问 | 日常个人使用（备选） |
| **`follow-dsh`（当前默认，已选定）** | 跟随 DSH 策略 | 跟随 DSH 策略 | **始终问**（`ctx.userQuestions`，仅根会话） | 信任 DSH 会话预设、追求顺畅 |
| `off` | 自动 | 自动 | 自动（仅日志） | 仅隔离测试环境，不推荐 |

> **当前环境的实际后果**：桌面 profile 默认 `danger-full-access` + 审批 `never`，所以在 `follow-dsh` 下，**日常读/写动作不会弹卡**（等于你授权模型操作浏览器）；只有上传/下载/eval/剪贴板/密码等硬敏感动作会单独弹确认。若想日常更稳，随时可切 `balanced`/`strict`。
>
> **硬敏感的实现注意**：`ctx.approval.request` 在 `never` 策略下会被自动放行，不能用来兜住硬敏感；硬敏感改走 `ctx.userQuestions.ask`（根会话可用；子代理会话调用会得到 `DELEGATED_CALLER`，此时直接失败并提示在根会话处理）。

其他相关配置：`approval.timeoutMs`（默认 120000）、`approval.trustScope`（`session` 默认 / `persistent` 后续）、`approval.sensitive`（硬敏感清单，后续可在设置页调整）。

## 6. 实现路径（P1 定稿）

1. **普通动作（P1 已实现）**：先读会话的 sandbox 模式——`ctx.sessions.get(exec.agent.id)` + `ctx.sandboxPolicy.resolve({session}).mode`；若为 `danger-full-access`，直接放行（会话预设已表达完全访问，不再额外问）。其他模式才调 `ctx.approval.request({agent, toolName, callId, reason, displayReason, signal})`；`allowed-once` 是唯一放行结果，`rejected/cancelled/unavailable` 都按失败处理（fail closed）。
   - 为什么不能只靠 `ctx.approval`：P1 真机实测，本会话的 approval answerer 会对插件发起的请求**自动拒绝**（返回 `rejected`），而 GUI 会话已是「完全权限」；只问 approval 会导致所有写操作不可用。
   - 当前硬敏感动作（上传/下载/eval/剪贴板/密码）尚未接入，P2 补 `ctx.userQuestions.ask`。
2. **硬敏感动作**：`ctx.userQuestions.ask({questions, agent, signal})` —— 无论会话策略如何都弹确认卡（根会话）；子代理会话（`DELEGATED_CALLER`）直接返回失败并提示到根会话处理。
3. **超时**：`AbortController` + `approval.timeoutMs`；超时 = 失败，不是默认允许。
4. 模型侧提示：系统提示词明确「审批被拒绝时不得重试同一动作，先向用户说明」。
5. 验收标准：普通动作在 `never` 下不弹卡（符合 `follow-dsh`）；硬敏感动作无论策略如何都会弹卡、拒绝路径返回明确错误、超时 fail closed。

## 7. 超时、无人值守与并发

- 超时：默认 120s，可配置；超时 = 失败，不是默认允许（fail closed）。
- 无人值守（goal/后台/子代理）：审批会挡住流程，这是**故意**的；模型应改为「先问人，再继续」。
- 并发：同一会话的审批串行；不同会话互不影响；审批卡上标明来源会话。
- 秒退/关会话：审批作废，不执行。

## 8. 审计（P2/P3）

- P2：会话内记录每次审批的 时间 / 会话 / 站点 / 动作 / 结果，工具 `chrome_diagnostics` 可查。
- P3：持久化审计日志（默认只存本机、可关闭），供排障与安全复核。

## 9. 明确不做

- 不自动点「允许」、不在超时后默认执行、不静默重试被拒绝的动作；
- 不把「本会话信任」扩展到硬敏感动作；
- 不用「是否继续？」这类模糊问法；文案必须写清 动作 / 站点 / 数据 / 后果；
- 不把审批结果当作页面内容可以伪造的东西（页面永远无法触发批准）。

## 10. 与 Claude/Codex 的对应关系

| 能力 | Claude in Chrome | Codex | 我们 |
|---|---|---|---|
| 首次访问站点授权 | ✅ 站点级 | ✅ confirmations | ✅ 首次动作询问 |
| 本会话信任 | ✅ allow all on site for session | ✅ | ✅ |
| 硬敏感动作确认 | ✅ 上传/登录等 | ✅ 发送/上传/权限/支付等 | ✅ 始终问 |
| 登录/CAPTCHA 交还 | ✅ 暂停等人工 | ✅ handoff | ✅ 截图 + 提示 |
| 审批被拒后行为 | 停止并说明 | 遵循确认策略 | `APPROVAL_DENIED` + 说明 |

## 11. 拍板记录

- **2026-10-17：默认模式定为 `follow-dsh`**（用户选择）。已知后果：当前 profile 默认 `danger-full-access` + 审批 `never`，因此日常读写不弹卡；硬敏感动作仍会走 `ctx.userQuestions` 单独确认。备选 `balanced`/`strict` 可随时切换。
- 后续若真实使用中出现误操作或误触站点，优先把模式调到 `balanced`，而不是给插件加更多特判。
